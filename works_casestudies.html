01

製造DX基盤

製造業ドメイン公開デモ入力から予定工数まで

旧Power Query × VBAケースの、整形・マスター結合・設定を外出しする考え方を継承。集計表を作るだけでなく、数量を作業量へつなぐ構造を説明します。

入力 INPUT：計画日・品番・数量を持つ元明細、品番と作業区分のルール、ライン、作業区分別の標準時間。元明細と共通マスターは読み取り専用で保持します。

処理フロー FLOW
[ INPUT：元明細を保持 ]
↓ 品番とルールを照合し、作業区分・ラインを確定
[ DAY LIST：日別明細 ] → [ CROSS LIST：品番×計画日 ]
↓ 作業区分ごとの標準分／個を照合
[ WORKLOAD：数量×標準分／個 → 日別・ライン別の予定工数 ]
設計判断 DESIGN
標準時間を品番へ直接結び付けず、作業区分を中間キーにする。同じ作業区分の品番は共通の標準時間を参照し、数量集計の可否と工数計算の可否を分ける。
例外処理 EXCEPTIONS
未登録品番・作業区分未解決・数量不正は数量集計から除外。標準時間欠落は数量を集計に残し、工数を未計算とする。いずれも0へ置き換えず、要確認として表示する。
検証 CHECK
元明細から日別・クロス集計の対象をたどり、計算例の数量×標準分／個を照合する。架空の不備例で、数量集計除外と標準時間未登録が別の判定になることを確認する。
結果 RESULT
日別・クロス集計から予定工数までを同じ明細に基づいて説明できる。未計算の数量も残るため、計算できた工数だけを全作業量と取り違えない構成にした。
Power QueryExcelVBAマスター照合標準時間
実装範囲 SCOPE：実運用の技術はPower Query / Excel / VBA。実運用構造を公開用HTML / JavaScriptで再現しています。公開v0の予定工数は数量×作業区分の標準分／個。段取り時間、能力超過判定、予実比較、CSV入出力、保存、自動日程計画は対象外です。
▶ 製造DX基盤デモを開く（別タブ）

旧版資料：旧PQ集計デモ・旧PQサンプルCSV。旧版固有の帳票・CSV導線と、現行デモの機能は区別しています。

02

図面・品番検索

製造業ドメイン公開デモ品番・部材・図面の照合

検索結果の名称だけで判断せず、関連材料・部材構成・図面まで確認できる導線を設計。製造DXと共通の品番・材料台帳を参照する公開デモです。

入力 INPUT：検索する品番、材料・厚み・分類の条件。共通台帳のproductId・materialIdを使い、図面検索用データは製品寸法・部材・図面との対応を追加します。品名・材料名・分類名は重複保持しません。

処理フロー FLOW
[ 品番検索：全角・半角／大小文字を正規化 ]
↓ 材料・厚み・分類で属性を絞り込み
[ 結果一覧 ] → [ 詳細・寸法 ] → [ 部材・関連材料 ]
↓ 登録されている図面を参照
[ 架空SVG ] → [ 拡大して確認 ]
設計判断 DESIGN
材料と厚みは、同一の関連材料が両方の条件を満たす場合だけ一致とする。分類は製品属性としてANDする。共通台帳のIDを参照し、デモごとの名称のずれを防ぐ。
例外処理 EXCEPTIONS
図面未登録、画像読込失敗、部材情報なし、寸法未登録、参照不整合、該当なしを区別して表示。欠落した寸法や部材を0・推測値で埋めず、確認できる情報の範囲を明示する。
検証 CHECK
材料条件と厚み条件を別々の材料だけが満たす製品を除外できるか確認する。検索→詳細→図面をたどり、例外表示と拡大の閉じる操作・Escape・元ボタンへのフォーカス復帰も確認する。
結果 RESULT
品番を手がかりに、関連材料・部材・図面を順に照合できる。検索に一致したことと、図面や寸法が登録済みであることを別に表示し、情報不足を見落としにくくした。
JavaScript品番検索共通マスター属性絞込SVG
実装範囲 SCOPE：公開v0は品番・属性検索から図面拡大まで。架空図面 / 製造使用不可。画像内容検索、OCR、印刷、保存、編集、CSV、Python処理、認証、改訂履歴は対象外です。原盤発注デモまで共通台帳に統合した構成ではありません。

03

原盤発注

製造業ドメイン公開デモ発注根拠をたどる

工場長としての「在庫を切らさず、持ちすぎない」という判断を、確認できる条件に分解。単一の発注結果だけでなく、元の出荷明細と計算根拠へ戻れることを重視しています。

入力 INPUT：日別の製品出荷、品番と原盤の対応、取り数、原盤・製品の現在庫、発注単位、安全在庫、リードタイム、営業日条件。公開用の内蔵サンプルとCSV読込を用意しています。

処理フロー FLOW
[ 出荷明細 ] → [ 品番・原盤マスター・取り数を照合 ]
↓ 発注方式に応じて必要原盤数・在庫推移を計算
[ 累計山到達 / 移動平均 / 在庫枯渇 ]
↓ 安全在庫・リードタイム・営業日条件を反映
[ 発注候補・必要数・期限 ] → [ 元明細と発注根拠を確認 ]
設計判断 DESIGN
発注方式と条件をマスターで選べるようにし、方式ごとの根拠を表示する。在庫枯渇型では製品在庫を先に使い、不足分だけ取り数に応じて原盤を消費。原盤単位と品番別の在庫管理も区別する。
例外処理 EXCEPTIONS
カット品マスター未登録、内製の原盤マスター未登録、取数未設定、別管理品は確認対象へ分ける。現在庫が未設定の場合は0として扱う既存仕様があるため、在庫設定と警告を確認して判断する。
検証 CHECK
同じ出荷明細に対して、在庫・取り数・安全在庫・リードタイムを変え、候補と根拠の変化を照合する。未登録品番を確認対象で確認し、デモCSVの読込結果から元明細までたどる。
結果 RESULT
発注候補から日別出荷・取り数・在庫推移へ戻り、候補が出た理由を確認できる。経験に基づく判断条件を共有する補助MVPであり、欠品防止や在庫削減の実測成果を示すものではない。
HTMLJavaScript営業日計算移動平均 / 安全在庫マスター駆動設計
実装範囲 SCOPE：公開版は在庫設定、方式切替、発注候補・根拠表示、CSV入出力、設定保存を備えた既存デモです。発注先への自動送信や本番システム連携は行いません。入力とマスターの対応・在庫の正しさが判断の前提です。

04

Receipt AI

AI監査公開デモ人間確定値を守る

旧OCRケースから「候補と確認工程を分離する」という考え方を引き継ぎ、主題を項目別の監査へ更新。V1では資料分類・人間監査・Ground Truth固定を運用し、公開版はその考え方を新規の架空資料で再現しています。

入力 INPUT：7件の架空Sourceと、あらかじめ用意したAI Observation。元資料・AI候補は読み取り専用です。人間の入力はReviewへ、確定値は項目別Ground Truthへ分けて保持します。

処理フロー FLOW
[ Source：元資料 ] → [ AI Observation：元の候補 ]
↓ HIGH / REVIEWはAI候補の判定。人間の確定とは別
[ Human Review：項目ごとの採用・修正・保留と根拠 ]
↓ 確定した項目だけ反映
[ Ground Truth：人間確定値 ] ← AI候補との差分を表示
設計判断 DESIGN
HIGHでも自動確定しない。元資料とAI候補はレビューで書き換えず、確定後も差分を残す。ファイル重複候補は資料のコピー可能性、transaction relationは別資料の同一取引・関連証憑の可能性として分ける。
例外処理 EXCEPTIONS
未取得値や不正な取引数は確定を拒否し、情報不足は根拠付きで保留。未確認・保留が残れば資料を確認完了にしない。画像読込失敗は確定を止め、参照不整合は操作を停止する。
検証 CHECK
1項目だけ確定しても未完了のままか、保留項目に確定値が生じないかを照合する。relation判定後もファイル重複候補と他資料のGround Truthが変わらず、AI候補も保持されることを確認する。
結果 RESULT
何をAIが候補とし、何を人が確定・保留したかを項目単位で追える。同日・同店・同額だけで取引を確定せず、根拠不足を判断不能として残せる。公開サンプルの件数はV1の処理・監査実績とは別である。

取引relationの人間判定は candidate（候補）、confirmed_same（同一取引・関連証憑と確認）、confirmed_separate（別取引と確認）、cannot_determine（判断不能・保留）。確定した同一／別取引の判定は固定し、判断不能は再検討できます。SHA完全一致やファイル重複だけで同一取引とは扱いません。

AI監査Human ReviewGround TruthrelationJavaScript
実装範囲 SCOPE：公開用架空デモ。操作結果は保存されず、再読み込みで初期化されます。ライブAI、OCR、SQLite、JSON保存、実SHA計算、外部API、モデル自動ルーティングは実装していません。V2 DB統合は使用していません。V1の運用実績とV2の将来設計を混同しない構成です。
